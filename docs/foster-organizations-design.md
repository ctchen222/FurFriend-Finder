## 使用者體驗

```text
所有訪客
  ├─ 找走失寵物（既有）
  ├─ 收容所動物（既有政府資料）
  └─ 中途之家（C1）
       └─ 公開介紹、地區、公開聯絡方式
            └─ 待認養動物（C2）

同一個已登入帳號
  ├─ 個人空間：我的協尋、個人通知、未來的認養申請
  └─ 組織工作空間：依成員權限管理
```

| 使用情境 | 未登入訪客 | 一般帳號 | 有權限的組織成員 |
| --- | --- | --- | --- |
| 查看已公開的中途之家與介紹 | 可以 | 可以 | 可以 |
| 查看已發布的動物（C2） | 可以 | 可以 | 可以 |
| 建立中途之家 | 先登入及驗證 Email | 可以申請 | 可以申請另一組織 |
| 查看組織草稿與後台 | 不可 | 不可 | 依角色 |
| 提出認養申請（C3） | 先登入 | 可以 | 可以，但不能審核自己的申請 |

公開頁不因閱覽者是成員而附加私人欄位。管理資料使用獨立 API，避免公共快取外洩。

### 前端頁面

- `/foster-organizations`：公開名錄，第一版以名稱、地區作精確／部分文字查詢，穩定分頁。
- `/foster-organizations/:id`：已審核且主動公開的介紹頁；不顯示成員 Email、私人住址、審查附件或內部備註。
- `/organizations/new`：登入且 Email 已驗證後建立組織。
- `/orgs/:id`：工作空間總覽，始終顯示組織名稱、角色、審核及公開狀態。
- `/orgs/:id/settings`、`/orgs/:id/members`：按權限管理；獨立的私人預覽頁不得出現在搜尋結果。
- 主導覽新增「中途之家」，保留既有視覺，不全面重設首頁。C1 不顯示尚不可使用的認養按鈕或假動物資料。
- 無結果、載入中、失敗重試、無權限及停權均有明確畫面；手機寬度與鍵盤操作納入驗收。

## 身分與權限

沿用既有 Email／Google 帳號；不建立組織共用密碼。一人可加入多個組織；個人中途亦建立單人組織，日後可邀請協作者。

| 能力 | Editor | Admin | Owner |
| --- | --- | --- | --- |
| 讀取一般工作空間資料 | 是 | 是 | 是 |
| 編輯動物草稿（C2） | 是 | 是 | 是 |
| 編輯公開介紹、發布／取消發布 | 否 | 是 | 是 |
| 邀請／移除 Editor | 否 | 是 | 是 |
| 指派／移除 Admin | 否 | 否 | 是 |
| 移轉負責人、關閉組織 | 否 | 否 | 是 |
| 處理認養申請（C3） | 否 | 是，排除自己的申請 | 是，排除自己的申請 |

平台 Reviewer 為獨立權限，只可審核／停權及讀取必要審核資料，不能因此取得認養申請或組織編輯權限。預設無人具有 Reviewer；初始授權走明確操作者工具並留稽核記錄，不能依 Email 字串或組織角色自動升權。審核者不得審核自己所屬的組織。

每次請求都查驗帳號、有效 membership、角色、資源 organization_id、組織狀態。敏感 mutation 的授權檢查與寫入使用同一交易及一致鎖順序，與停權／撤權串行化。

### 工作空間切換

- organization_id 取自當次 URL，不以全域 session 的 activeOrganizationId 決定寫入目標。
- 一般登入回到個人空間；合法的組織深連結登入後回原頁，再由伺服器檢查權限。
- 快取鍵包含 user_id、organization_id 與查詢；切換時取消舊請求並丟棄過期回應。
- 多分頁可分別管理 A、B 組織；切換不可把既有草稿重新指定到另一組織。
- 未儲存表單需提示；登出、換帳號清除私人快取；重新登入不可自動重送舊 mutation。
- 被移除後下一次 API 請求即拒絕。已經看過的畫面無法追回；重新聚焦／重新驗證時清除失效內容。

## 資料模型及狀態

新增獨立資料表，不把 `animal_shelter` 直接改成 organizations，也不把政府動物搬進組織。

| 模型 | 核心資料與限制 |
| --- | --- |
| organizations | ID、名稱、INDIVIDUAL/GROUP、公開介紹、地區、自願公開聯絡方式、review_status、operational_status、published_at、version |
| organization_memberships | organization_id + user_id 唯一；角色、ACTIVE/REMOVED；每個未關閉組織恰有一名有效 Owner |
| organization_invitations | 組織、受邀 Email、角色、token hash、邀請者、到期、接受／撤銷狀態 |
| organization_ownership_transfers | 原 Owner、受讓有效成員、到期、接受／撤銷狀態；同組織最多一筆待處理 |
| organization_reviews | 申請版本、審核者、結果、理由、時間；私人資訊不進公開投影 |
| platform_roles | user_id + 明確平台角色；記錄授權與撤銷 |
| organization_audit_events | actor、org、動作、目標、結果、時間；不記密碼、邀請原始 token 或完整私人內容 |

- 審核：PENDING → APPROVED 或 REJECTED；拒絕後修改可重送。
- 營運：ACTIVE／SUSPENDED／CLOSED，與審核狀態分離。
- 公開條件：APPROVED + ACTIVE + published_at 非空。審核通過不自動公布私人資料。
- 名稱及組織類型改動須重新審核並暫停公開；介紹、地區、公開聯絡方式可由 Admin/Owner 更新，保留稽核。
- PENDING/REJECTED 可修改設定、管理成員及私人預覽，但不能公開；SUSPENDED 僅提供狀態及申訴所需讀取，不接受一般管理寫入；CLOSED 不接受新活動。
- 關閉不硬刪資料。C3 上線後必須補上未結案申請的關閉前檢查。帳號刪除不可 cascade 刪除組織。
- 對存在上限一名 Owner 的 DB 約束，加上建立／移轉／退出交易保證至少一名；不能僅靠前端避免零 Owner。

### 邀請、移轉及 Email

- 邀請只有已驗證且符合受邀 Email 的使用者可以接受；錯誤 Google 帳號顯示切換提示，不自動綁定。
- 邀請有效期 7 天、一次性、可撤銷；重送撤銷舊邀請並產生新 token。重複接受已成功的邀請回傳原結果，不重複建立 membership。
- 接受時再次檢查邀請者目前權限、組織狀態與邀請角色；既有成員不得透過邀請隱式升權。
- Owner 移轉有效期 24 小時，需受讓成員接受；同一交易完成角色交換與稽核，原 Owner 降為 Admin。撤權／過期／平行移轉不得產生零 Owner 或雙 Owner。
- 唯一 Owner 不能直接退出或刪除帳號；須完成移轉或關閉。帳號失效時走有紀錄的人工恢復，不開放其他成員自我升權。
- 邀請與移轉信採組織用途的持久寄送工作，不沿用走失動物通知偏好作寄送條件；worker 發送前確認事件仍有效。
- DB 僅保存 token hash；可重送的寄信 payload 若包含原始 token，須加密、設定有效期並在完成後清除，不可明文放在 audit／log。
- SMTP 失敗可重試，邀請狀態可見且可重新寄送；不承諾 SMTP exactly-once。C1 的邀請寄信以 Mailpit 驗證，外部收件另行人工確認。

## 實作邊界與既有整合點

- 新增組織 domain policy、service、repository、validation 及公開／私人 response contracts，避免把所有邏輯塞進 `src/router/webApiRouter.ts`。
- 公開 organization router 必須在登入強制檢查之外；私人 router 沿用有效 session 與 same-origin 檢查，另外增加逐請求 organization authorization。
- 交易沿用 `src/libs/transaction.ts` 的同一 client 模式。政府 API 匯入不受新組織模型影響。
- React 路由及 `src/router/reactWebRouter.ts` 的 HTML 路由白名單一起更新，直接開頁／重新整理皆正常。
- `web/src/features/auth/AuthPage.tsx` 的 returnTo 白名單需加入明確合法的組織路徑，拒絕外部 URL；Email 與 Google 登入皆測試。
- 私人錯誤：未登入 401；非成員或跨組織資源 404；成員缺少動作權限 403；版本／生命週期衝突 409；欄位驗證 422。訊息不得暴露其他組織內容。
- 公開 API 對未發布／不存在組織一致回 404；每次讀取檢查公開條件。未建立可靠失效機制前不加入長效公共快取。

## C2 搜尋方向：待確認的延伸提案

搜尋目的必須分開，不能讓同一組「喜歡程度」分數控制兩者。

| 模式 | 問題 | 策略 |
| --- | --- | --- |
| 走失匹配 | 是否可能是同一隻動物？ | 保留時間／地點／外觀證據及未知值；新增語意召回需另外通過 matching 評估 |
| 認養探索 | 哪些動物符合照顧能力與偏好？ | 必要條件過濾，偏好加權，顯示符合原因及資料不足 |

三種方案：

1. 條件篩選 + 別名／部分文字搜尋：可解釋、易驗收，作為 C2 第一版。
2. 加文字近似比對：容忍拼寫差異，但不能理解「親人」的語意；用實際中文資料驗證後再加入。
3. 自然語言解析／語意搜尋：可處理整句偏好，但成本與誤判面較大，另立 C2 後續實驗，不直接採用。

PostgreSQL `pg_trgm` 提供字元相似度與索引，並非寵物特徵語意模型；中文短詞、別名與否定條件需要獨立測試。來源：[PostgreSQL 17 pg_trgm](https://www.postgresql.org/docs/17/pgtrgm.html)。

建議 UI 示例：「台北、成貓、親人、可與其他貓同住」轉為可修改的條件標籤。使用者明確指定的必要條件不能偷偷放寬；沒有結果時提出放寬建議並等待使用者操作。條件變更重置游標，查詢與排序使用相同條件及穩定 tie-breaker。

行為及健康資訊由刊登者明確填寫並附觀察時間／說明；UNKNOWN 不視為符合。不能從照片推論親人、無病、適合小孩，也不能把「不親人」命中為「親人」。未來語意結果必須顯示可追溯的符合原因，不宣稱保證適合。

政府收容資料與組織刊登保留來源標籤和各自 ID／生命週期。公開搜尋只讀取符合公開條件的投影；草稿、停權、私人欄位不能進結果、計數或搜尋索引。政府資料是否可認養依來源狀態呈現，不默認能站內申請。

走失候選集不自動納入所有中途待認養動物。若未來納入「拾獲待尋主」刊登，另定拾獲時間／地點、來源驗證、去重與候選資格，並驗證召回品質。
